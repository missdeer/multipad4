# GitHub issue 解决工作流

主代理负责队列、分配和合并协调，尽量把实现及交付工作交给两个子代理。每个 issue 由同一个子代理独立负责，直到 PR 合并、issue 关闭。

默认跳过独立评审渠道，不启动交叉检查或多代理评审；仍须处理 GitHub 上实际出现的评审意见和 CI 失败。用户本轮明确要求的检查优先。

## 范围与授权

- 指定 issue 时只解决指定任务；要求清空队列时，持续领取当前仓库的开放 issue，直到分页复查为零。PR 不算 issue。
- 用户请求执行本流程时，在指定仓库和任务范围内完成代码修改、提交、推送、PR 创建、必要讨论回复、合并及合并后的远程分支/本地 worktree/本地分支清理，无需逐步重复确认。仅查看或规划的请求不授权这些操作。
- 不把“清空”理解为直接关闭未解决的 issue，也不顺带合并无关的机器人 PR。
- 遇到需求歧义，先读 issue 正文、评论、附件及关联任务，继续不受影响的工作；确需用户决定时，只问阻塞点。
- 认证、权限、外部服务或必需信息阻塞时，报告具体阻塞和未完成任务。不要绕过分支保护、必需检查或审批；不要无限重试同一失败。

## 领取与隔离

1. 读取仓库 `AGENTS.md`、项目范围及构建约定；检查 remote、默认分支、工作区状态和已有 worktree。保护用户未提交及未跟踪文件。
2. 优先使用可用的 GitHub 插件；能力不足或认证失败时改用已登录的 `gh`。由 remote 确认仓库，不硬编码上一次运行的仓库、分支或 issue 编号。
3. 分页列出开放 issue 和 PR，检查是否已有分支、PR 或负责人正在处理，避免重复实现。确认依赖关系，优先领取可独立完成的任务。
4. 开启两个子代理，每人领取一个不同 issue；每个 issue 使用独立分支及 worktree，构建目录和临时文件也归该 worktree。禁止共享 CMake cache 或在主工作区并行写代码。
5. 只有一个 issue 时，一个子代理独立实现，另一个只监控队列和 PR；无任务时不要编造任务、拆出交叉评审或重复修改同一 issue。
6. 主代理维护简短状态：issue、负责人、worktree、分支、PR、阻塞和下一步。任务完成后立即分配下一个可领取 issue；共享文件或依赖会冲突时安排顺序。

派发时明确给出：issue URL、隔离位置、仓库规则、验收要求、提交推送及合并授权、跳过独立评审和交叉检查、由谁执行合并。要求子代理自主完成下列整个循环，避免每个步骤都等待主代理。

## 子代理的交付循环

1. **实现。** 读取 issue 及相关代码，搜索调用者，确定受影响的接口、资源和测试。复用已有实现，修复根因，保留数据保护和错误处理。遵守项目性能优先级；不增加无关功能或依赖。
2. **验证。** 完成基本编译和冒烟测试；非平凡改动补最小有效回归。视觉变化按仓库要求提供截图。测试通过后立即提交，不等待不可用的独立评审渠道。未做的手工检查如实记录。
3. **提交并推送。** 遵守仓库及可用 commit 技能约定，按文件暂存自己的改动，保留 hooks 和签名。推送专属分支，禁止强推默认分支。需要更新 PR 分支时优先普通推送；确需重写仅对自己的分支使用带 lease 的推送。
4. **创建 PR。** 一个 issue 对应一个聚焦的 PR；正文写清问题与最终行为、`Closes #编号`、验证结果及剩余手工检查。已有 PR 时更新它，避免重复创建。多行正文用结构化参数或 `gh --body-file`，保留真实换行。
5. **监控当前提交。** 跟踪 PR 的最新 head、CI、评审线程和合并状态；旧 head 的成功不能作为新提交的通过证据。每约 60 秒轮询，遇到限流或网络瞬断退避，避免忙等。
6. **处理评审。** 阅读实际意见，修复确认属于任务范围的问题，补相关回归并重跑受影响检查，推送同一 PR。回复处理方式，问题解决后再 resolve；有依据地说明不适用的意见，不能为合并而忽略有效问题。同类边界问题一次修复根因，避免逐字符特例。
7. **处理 CI。** 读取失败作业日志并修复原因；仅明确的临时故障才重跑，不能反复重跑掩盖稳定失败。可取消同一 PR 已被新提交替代且仍占资源的旧运行；保留最新运行，不取消其他 PR 或默认分支运行。
8. **处理冲突。** 同步默认分支，在自己的 worktree 解决冲突，保留双方有效行为，重跑受影响的编译和冒烟检查后推送。主代理只协调依赖和合并顺序，无需重新检查实现。
9. **合并。** 当前 head 的预期 CI 全部成功、必要检查满足、有效评审问题处理完且无冲突时立即合并，使用仓库允许的方式。仅因触发条件而跳过的非预期作业可保持 skipped。只有一名明确负责人执行合并，避免主代理和子代理重复操作；不额外等待未要求的评审。
10. **收尾。** 确认 PR 确实 merged、issue 已关闭；按下节删除对应远程分支、本地 worktree 和本地分支，报告合并提交、验证及清理结果。若自动关闭未生效，核实任务完成后再关闭。重新领取任务前刷新队列。

## 合并后清理（每个 PR 必做）

- 领取任务时记录专属 worktree 的绝对路径、远程及分支名。只清理本次任务的资源，不删除默认分支、用户工作区或其他代理的分支/worktree。
- 确认 PR 为 merged，记录其最终 head SHA；核实待删除的本地及远程分支仍指向该 SHA。若已出现新提交，保留相应资源并报告，不能删除后续工作。
- 从主工作区或其他保留目录执行清理；确认实现代理已停止使用该 worktree，无未提交或需保留的未跟踪文件。清理生成文件前验证绝对路径确实位于该任务 worktree 内，不使用通配符或强制删除 worktree。
- 删除 PR 的远程 head 分支（例如 `git push <remote> --delete <branch>`）；平台已自动删除时视为完成。不要依赖 `gh pr merge --delete-branch` 自动处理独立 worktree 的本地清理。
- 使用 `git worktree remove <absolute-path>` 删除该 worktree，再用 `git branch -d <branch>` 删除本地分支。squash/rebase 合并可能无法通过祖先检查；仅在已核实 PR 合并且本地分支精确匹配最终 PR head、没有额外工作时允许 `git branch -D <branch>`。
- 最后核实远程分支、本地分支及 worktree 均已不存在。权限、文件占用或未保存工作导致清理失败时，保留现场并报告具体残留，不把它标为清理完成。

## 当前仓库的构建约定

以最新 `AGENTS.md` 为准。MultiPad4 是 Windows C++/Win32 项目，每个 worktree 内使用自己的 `cmake-msvc-build/`。若 cmake-build/commit 技能可用，先读取并遵守；不要直接调用 cmake 或 ninja 绕过构建包装器。

```powershell
bash -lc "cmake-reconfigure cmake-msvc-build"
bash -lc "cmake-build cmake-msvc-build"
ctest --test-dir cmake-msvc-build --output-on-failure
```

首次配置或更改 `CMakeLists.txt` 时重新配置。CTest 包括文件 I/O 与编辑器集成冒烟；查看当前 CI 是否启用了这些测试，不能把仅编译成功当作冒烟通过。动态读取 CI 配置，不固定矩阵数量或工具链版本。

## 队列完成标准

- 指定任务全部合并并关闭；清空模式还须再次分页确认开放 issue 为零。
- 最后检查自己创建的 PR 是否仍有未处理的 CI、评审或冲突。遇到真实阻塞时明确列出，不能声称已清空。
- 所有已合并任务的远程分支、本地 worktree 和本地分支均已清理；有保留项时明确列出原因。
- 将本地主分支安全地 fast-forward 到远端默认分支；存在用户改动或分叉时保留现场，不强制 reset。不要因同步后的重复构建延误已验证的交付，除非出现新的风险。
- 最终简报给出解决的 issue、PR、合并提交、构建/测试/CI 结果；末尾说明跳过的检查和实际限制。新出现的无关机器人 PR 不扩大本轮范围。
