# 全文读取路径：分段计时与对照实验

日期：2026-11-13。结论适用于本机及本次输入，未测冷盘或其他机器。

主要成本是全文流式读取中的映射页访问、临时缓冲区分配/复制，以及映射窗口回收；现有 UTF-8 校验已经使用 SIMD。这个随机文本是 ASCII / UTF-8，实验中的实际转码字节数为 **0**，不能把整个旧计时区间称为转码成本。

当前全文路径采用复用缓冲区的缓存 `ReadFile`，大文件最多四个参与线程执行已有 SSE4 SIMD 校验。只读 Fast View 仍使用按需映射，不受全文路径选择影响。

## 计时方法的修正

此前“读取/校验/解码 2.95 秒”由 `GetTickCount64` 累计小块时间并相减得到。它的粒度不足以精确归因，后来在同一路径也出现 6.34 秒，不能把 2.95 秒当成固定或精确的阶段基线。

现在：

- 文件层直接用 QPC，分别记录打开/换映射、分配/复制或 `ReadFile`、探测、校验、转码、消费者回调和总时间。
- 编辑器用 `std::chrono::steady_clock` 记录换行扫描和 Scintilla 插入，消除旧时钟在短区间累加中的偏差。
- 记录源读取请求字节、实际校验字节、转码字节、交付字节和进程缺页计数。
- 比较读取后端时使用只累计字节数的消费者，排除 Scintilla。
- 每项先预热一轮，再测五轮；最终对照在同一进程交错执行旧算法和新算法，并交替先后顺序。
- 原始逐轮输出、CSV 和机器信息保存在 [performance/large-file-read-2026-11-13](performance/large-file-read-2026-11-13/summary.json)。没有增加不稳定的耗时通过阈值。

映射第一次访问文件页的成本记在**真正访问该页的操作**里。因此删掉复制后，计时可能从“复制”转移到“校验”，这不代表 SIMD 校验计算突然变慢。

`PageFaultCount` 包含软缺页，不能当作磁盘读取次数。软缺页可以不访问后备存储：[Microsoft Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)。本实验没有用 ETW 区分硬缺页、软缺页及物理磁盘请求，不能进一步给出“纯磁盘耗时”。

## 环境与输入

- Intel Core i9-12900HK，14 核 / 20 逻辑处理器，约 32 GiB 内存。
- Windows 11 10.0.26300，MSVC，`RelWithDebInfo`，`/O2 /Ob1`，`MULTIPAD4_SIMD=SSE4.2`。
- 同一 `tmp/random-text-5GiB.txt`，5368709120 字节；已另行逐块确认全部是 ASCII。SHA-256：`5ac1ca64feb2c139decf370968c91cfd6122b25256645e8e3e2cb7821f941e27`。
- 两条路径均读取并校验完整 5 GiB，交付 5368709120 字节；源请求 5369760256 字节，多出的少量数据来自首部样本和字符边界前瞻。
- 未清空系统文件缓存，没有并行运行其他测试或构建作为负载。频率、调度、内存分配器和缓存状态仍会波动，以下提供范围。

## 同进程交错对照

旧算法参考实现 `ReferenceCopiedRead` 重现原显式 UTF-8 路径：映射窗口 → 每块新建字符串复制 → 单线程 SIMD 校验。它保留在测试代码中，便于以后在同一可执行文件中重测。

| 方案 | 中位数 ms | 最小–最大 ms | 中位轮缺页数 |
|---|---:|---:|---:|
| 旧算法参考实现 | 3742.152 | 3394.237–4673.951 | 2627471 |
| 复用缓冲区的 ReadFile + 4 线程 SIMD | 1087.699 | 1047.958–1257.800 | 4636 |

总时间减少约 **70.9%**，吞吐约为原来的 **3.44 倍**。这是文件层结果，不能当作整份文档已经可编辑的时间。

中位轮分段（同一轮取值，可以检查加总，剩余为探测、循环、释放及计时开销）：

| 阶段 | 旧算法 ms | 新算法 ms |
|---|---:|---:|
| 打开 / 换映射 | 506.383 | 0.051 |
| 分配、复制 / 缓存 ReadFile | 2606.502 | 933.891 |
| UTF-8 校验 | 350.765 | 152.121 |
| 实际转码 | 0 | 0 |

原始 [逐轮 CSV](performance/large-file-read-2026-11-13/paired.csv) 和 [完整输出](performance/large-file-read-2026-11-13/paired.txt)。更早对原实现加 QPC 的独立五轮基线是 3315.525 ms（3276.512–3350.151 ms），见 [initial-baseline.txt](performance/large-file-read-2026-11-13/initial-baseline.txt)。旧路径存在显著分配/页访问波动，所以不只报告一次最优结果。

## 拆分读取方式和并行度

另一轮后端扫描，每项预热后五轮。表中分段列各自取中位数，不一定来自总时间的中位轮。

| 后端 | SIMD 参与线程 | 总时间中位数 ms | 最小–最大 ms | 校验区间中位数 ms |
|---|---:|---:|---:|---:|
| 直接映射，无中间字符串 | 1 | 2168.044 | 2161.616–2192.646 | 1618.782 |
| 直接映射，无中间字符串 | 2 | 1508.039 | 1501.870–1517.329 | 957.582 |
| 直接映射，无中间字符串 | 4 | 1172.184 | 1159.190–1184.292 | 616.768 |
| 直接映射，无中间字符串 | 8 | 1083.694 | 1077.422–1095.826 | 520.729 |
| 缓存 ReadFile，复用缓冲区 | 1 | 1315.549 | 1309.564–1326.876 | 323.124 |
| 缓存 ReadFile，复用缓冲区 | 2 | 1160.105 | 1156.527–1169.372 | 187.240 |
| 缓存 ReadFile，复用缓冲区 | 4 | 1134.688 | 1128.085–1182.309 | 124.252 |
| 缓存 ReadFile，复用缓冲区 | 8 | 1112.496 | 1095.994–1116.715 | 136.994 |

直接映射单线程每轮约 1313644 次缺页，缓冲读取单线程约 4620 次。直接映射的“校验区间”还承担文件页的首次访问；缓冲读取的校验面对已填好的缓冲区，两者不能作为纯计算速度直接相除。

独立的常驻内存校验实验，对 64 MiB 样本重复扫描 32 次，总计 2 GiB，1 / 2 / 4 / 8 线程的中位数分别为 131.468 / 77.612 / 45.432 / 30.680 ms。这确认 SIMD 计算本身能并行加速，但它并不是整个旧读取区间的全部工作。

8 线程映射在扫描实验中略快，但使用更多线程并产生大量缺页。当前默认选缓冲读取、最多 4 线程，避免为很小的额外收益增加并行度；后端和线程数保留在内部 `ReadOptions` 中供其他机器复测。[完整扫描数据](performance/large-file-read-2026-11-13/backend-workers.txt)。

## 接回真实 Scintilla 后

三个独立编辑器进程完整载入同一个 5 GiB 文件，全部使用新的高精度计时。下表阶段取总时间中位轮（第 3 个进程）：

| 阶段 | 时间 ms |
|---|---:|
| 读取 / 校验 / 探测 / 文件层其他开销 | 1685.996 |
| 其中缓存 ReadFile / 样本复制 | 1521.976 |
| 其中 UTF-8 校验 | 161.060 |
| 其中实际转码 | 0 |
| 换行扫描 / 行表预留 | 388.382 |
| Scintilla 插入 / 行索引构建 | 1572.361 |
| 完整流式载入总时间 | 3646.732 |

三个进程读取区间分别为 1807.697、1647.999、1685.996 ms；完整流式载入为 3770.181、3529.450、3646.732 ms。消费者写入大量内存会影响缓存和内存管理，所以不能直接把空消费者的 1.088 秒当作真实编辑器读取阶段。

这也说明现在文件层剩余成本主要在缓存读取和数据供给；SIMD 校验只占这个实际读取区间约 9.6%。进一步只优化校验，不能消除另外的约 1.52 秒。

原始数据：[editor-0.txt](performance/large-file-read-2026-11-13/editor-0.txt)、[editor-1.txt](performance/large-file-read-2026-11-13/editor-1.txt)、[editor-2.txt](performance/large-file-read-2026-11-13/editor-2.txt)。缺页数包含 Scintilla 消费者内存活动，不能与空消费者的缺页数混用。

## 旧方案与新方案的可编辑端到端交错对照

随后增加真实编辑器端到端比较，避免把文件层吞吐外推为整体提升。两种读取策略接入相同的 `EditorDocument::LoadStream`、Scintilla 文本/行表、样式设置和绘制流程。旧方案是原显式 UTF-8 读取算法的参考复现，不是另一份旧版本完整可执行文件。

同一进程先各预热一次，再交错各测五次，奇数轮交换先后。每次创建新的真实 MDI 文档，上一份完整文档已释放。计时从创建文档前开始，到全文加载、设置可编辑、刷新状态和同步首屏绘制完成为止；不包含进程启动、测试验证及关闭文档。

| 方案 | 完整可编辑加载中位数 ms | 最小–最大 ms |
|---|---:|---:|
| 旧读取算法 + 相同 Scintilla 流程 | 6129.949 | 6105.209–6534.458 |
| 新读取算法 + 相同 Scintilla 流程 | 3579.671 | 3309.017–3800.971 |

端到端中位数比为 **1.712 倍**，耗时减少 **41.604%**。这批数据支持本机整体约 1.7 倍的加速，不支持整体 2–3 倍的说法。

分段各自取五轮中位数（不保证来自同一轮，不能直接相加得到总时间中位数）：

| 阶段 | 旧方案 ms | 新方案 ms |
|---|---:|---:|
| 读取相关区间 | 4204.297 | 1416.262 |
| 换行扫描 / 行表预留 | 397.255 | 391.825 |
| Scintilla 插入 / 行索引 | 1574.545 | 1768.393 |

读取阶段约加速 2.97 倍，但其余阶段没有相同幅度的收益；Scintilla 插入在这轮新方案中还略慢，不能据此推断其原因。必须使用实测总时间判断整体加速。

每次均校验完整长度 5368709120 字节、行数 41943041、末行位置、头/中/尾源字节片段、EOF 跳转、追加字符和撤销后的保存点状态，确认是完整可编辑文档，非局部 Fast View。验证在计时结束后执行；原文件保持只读访问。

## 实现和验证

- 全文流默认采用缓存 ReadFile，复用约 16 MiB 输入缓冲区。需要映射的调用仍可显式选择映射后端。
- 映射后端把有界 string_view 直接交给同步消费者，移除逐块临时字符串。编码转换也接受 string_view，避免无条件复制原始输入。
- UTF-8 探测成功后不在第二遍重复执行相同校验。自动探测仍保留先验证、必要时整份使用回退编码的行为；其数据交付仍需第二遍读取，不能宣称变成单遍 I/O。
- 大文件 UTF-8 使用一次创建的工作组，调用线程参与其中，最多另建 3 个工作线程。每块内按完整 UTF-8 字符划分，全部线程完成后才复用输入缓冲区。
- Scintilla 消费回调仍只在调用线程执行。线程创建失败、非法 UTF-8、消费者抛异常时均收束工作线程。
- 回归覆盖两个后端、1/2/4/8 线程、跨工作分区和跨 I/O 块的四字节字符、非法代理项编码、自动探测、消费者异常、各类编码原有往返行为以及完整编辑器流程。
- 6 项 CTest 全部通过。非 ASCII 校验和其他编码转码的性能没有用本次 ASCII 文件代替实测。

## SIMD、OpenCL 和下一步判断

SIMD 原先已经启用，本次没有通过提高全局最低指令集来获得收益，仍保持 SSE4.2 构建。线程并行有实测收益，主要收益则来自改变数据供给方式及减少分配、复制和映射页开销。

**没有运行 OpenCL / GPU 性能实验，也没有对 AVX2 做 A/B 测试**，因此不声称 GPU 或更宽 SIMD 一定更快或更慢。OpenCL 若继续评估，必须测端到端的主机数据准备、内存传输/映射同步、内核及结果同步，不能只测内核；参见 [Khronos clEnqueueWriteBuffer](https://registry.khronos.org/OpenCL/specs/unified/refpages/man/html/clEnqueueWriteBuffer.html)。按当前中位轮，即使把 CPU 校验的 152.121 ms 完全消掉，空消费者读取总时间的理论改善也只有约 14%，实际编辑器读取区间的上限约 9.6%。

磁盘冷读、网络盘、不同编码、不同 CPU 和内存压力需要另做同样的对照；没有根据这批热缓存数据承诺所有机器的速度。

